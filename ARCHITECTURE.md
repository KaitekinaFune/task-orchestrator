# Архитектура

## Устройство

Локальный сервер на Node.js без runtime-зависимостей обслуживает веб-интерфейс на loopback, хранит данные и запускает дочерние процессы. Клиент — один файл без сборки; он опрашивает состояние и выводит данные агентов только через `textContent`. Основная платформа — Windows. happy-dom нужен только для DOM-тестов.

| Модуль | Назначение |
| --- | --- |
| `supervisor.mjs`, `supervisor-action.json` | Промпты, схема действия и её проверка, расчёт итогового статуса |
| `runs.mjs` | Движок: цикл супервизора, запуск воркеров и проверок, очередь, блокировки, журнал |
| `claude.mjs`, `codex.mjs`, `agents.mjs` | Адаптеры CLI: аргументы, запуск, разбор потока |
| `workspace.mjs`, `snapshots.mjs` | Состояние Git, отпечаток файлов, снимки и diff |
| `usage.mjs` | Журнал расхода и его сводка для страницы «Расход» |
| `profiles.mjs`, `credentials.mjs` | Окружение профилей, ключи в Windows Credential Manager |
| `server.mjs`, `app.js` | HTTP API и интерфейс |

## Супервизор и воркеры

```
задача → супервизор → действие (JSON) → проверка → оркестратор выполняет → журнал → супервизор → …
```

**Супервизор** — процесс CLI, запускаемый заново на каждое решение. У Claude это `--tools "" --strict-mcp-config --no-session-persistence --json-schema` в режиме `default`: инструментов нет, поэтому ответ может быть только действием. Режим `plan` не используется, потому что смещает выбор модели в сторону чтения. Codex запускается с `read-only`, `--ephemeral` и `--output-schema`: отключить инструменты там нельзя, он может читать файлы.

Сессия супервизора не сохраняется. Весь контекст — журнал задачи, из которого каждый раз собирается промпт, поэтому перезапуск сервера ничего не теряет. Старые ответы воркеров в промпте сокращаются до 1000 символов; полные (до 8000) идут только у трёх последних.

**Действия:** `run_workers`, `run_checks`, `get_diff`, `ask_user`, `finish`. Некорректный ответ возвращается супервизору с причиной один раз, второй останавливает задачу со статусом «ошибка». Ошибка самого CLI супервизора (авторизация, лимит) сразу завершает задачу с текстом ошибки.

**Воркер** — процесс CLI с заданием от супервизора. Движок всегда добавляет к заданию исходную задачу и правила: не делать commit/push/merge/reset/clean, сохранять чужие изменения. Пишущий воркер работает в режиме `auto` (`acceptEdits` для DeepSeek) или `workspace-write` у Codex; воркер на чтение — `plan` без инструментов записи или `read-only`, без сохранения сессии. Сбой или таймаут воркера не останавливает задачу: результат уходит супервизору, и решает он.

**Изображения** передаются супервизору при каждом решении и каждому новому воркеру; продолжаемая сессия получает только те, что появились после её прошлого хода. Claude получает их блоками `image` через `--input-format stream-json`, Codex — флагами `--image=<путь>`. Запуски без изображений остаются текстовыми. Если файл изображения пропал, агент не запускается и шаг завершается ошибкой: молча потерять картинку нельзя. В промпте текст на изображениях помечен как данные задачи, но это не гарантия: как и для внедрения через код, границы держат инварианты и режимы CLI.

## Инварианты в коде

Это проверяет движок, а не промпт:

- Запускаются только агенты из настроенного списка; модель называет запись списка, а не профиль.
- Пишущий воркер работает один; воркеров на чтение — до четырёх одновременно.
- Команды запускаются только из проверок проекта; супервизор указывает их id. Источником команд никогда не становится вывод модели.
- Продолжить можно только пишущего воркера того же агента с сохранённой сессией.
- Лимиты на один запуск: 40 решений, 20 запусков воркеров, 120 минут; процесс воркера — 30 минут, решение супервизора — 5 минут. Сообщение пользователя начинает новый отсчёт.
- Разрешения берутся только из сохранённых отказов CLI и только по явному действию пользователя. Супервизор выдавать их не может. Разрешения действуют на пишущих воркеров Claude этой задачи.
- Статус считает движок: итог `done` с проваленными или устаревшими проверками становится «требуется решение».
- Bypass-режимы не используются.

## Известный риск

Ответы воркеров, вывод проверок и diff попадают в промпт супервизора, а его решения становятся заданиями воркеров. Инструкция, внедрённая в код или логи, может повлиять на задание пишущего воркера. Промпт помечает эти данные как недоверенные, но это не гарантия. Границы, которые держатся независимо от модели, — инварианты выше и ограничения самого CLI: воркер не получает прав сверх своего режима, а команды оркестратора не берутся из текста. Режим `auto` решает классификатор CLI, поэтому подключайте только репозитории, которым доверяете.

## Данные

`state.json` — проекты, задачи, настройки, профили. `usage.jsonl` — журнал расхода: одна строка на процесс агента, только счётчики и идентификаторы, без текстов; при удалении задачи остаётся. `runs/<taskId>.json` — журнал задачи, у каждой задачи свой файл, запись не чаще раза в 500 мс и только при изменениях. Вывод процессов ограничен 256 Ки символов (начало и конец); секреты профиля вырезаются. Интерфейс получает последние 16 000 символов журнала, полный — по запросу. Задача имеет один запуск: сообщения продолжают тот же журнал, повторных «попыток» нет.

`images/<taskId>/` — приложенные изображения, в состоянии и журнале хранятся только их идентификаторы, тип и размер. Они не попадают в checkout и снимки и удаляются вместе с задачей. Лимиты: 5 штук за запрос, 10 на задачу, 3,75 МБ на файл и 15 МБ на задачу, чтобы запрос к API оставался в его пределах. Тип определяется по байтам, SVG не принимается.

Данные версии с режимами при запуске копируются в `state.before-supervisor.json` один раз, а из состояния удаляются попытки и пресеты. Задачи остаются и могут быть запущены заново; старые журналы в интерфейсе не показываются.

Запись журнала: `user`, `answer`, `decision`, `workers`, `checks`, `diff`, `note`.

## Git и снимки

Файлы хешируются при старте, после каждого пишущего воркера и в конце, а не после каждого шага: на крупном репозитории это самая медленная часть. Отпечаток не учитывает игнорируемые файлы и submodules. Снимок — Git-дерево во временном индексе (`GIT_INDEX_FILE`) с отдельным каталогом объектов; индекс и объекты пользователя не меняются. Diff бывает на всю задачу, на воркера и «до запуска»; `--no-ext-diff` и `--no-textconv` исключают запуск команд из настроек репозитория.

Проверка действительна только для файлов, на которых выполнена. Разделить правки агента и внешние правки во время работы нельзя, и приложение этого не утверждает.

## Очередь и блокировки

Одна директория — один активный запуск, всего до трёх. Остальные ждут в очереди. Пока задача ждёт ответа, блокировка не удерживается: другая задача может изменить те же файлы, и старые проверки устареют.

После аварийного перезапуска активные запуски отмечаются прерванными. Новая работа запрещена, пока пользователь не подтвердит, что старые процессы остановлены: запущенный CLI мог пережить сервер. Затем задачу можно продолжить сообщением, супервизор исходит из журнала. Присоединения к работающему процессу нет.

## Безопасность

- Сервер слушает только loopback и проверяет Host. Изменяющие запросы требуют Origin и токен. Изображения отдаются только по идентификаторам из записей задачи, с `Cross-Origin-Resource-Policy: same-origin` и `nosniff`.
- Дочерние процессы запускаются без shell, задание передаётся через stdin.
- Ключи хранятся в Windows Credential Manager, для каждого процесса формируется отдельное окружение. Подписка использует штатную авторизацию CLI; её токены приложение не собирает.
- CLI может исполнять настроенные пользователем hooks и MCP. Подключение репозитория означает доверие к нему. Супервизор Claude MCP не загружает.
- Логи могут содержать секреты, не совпадающие с известными значениями: полной очистки приложение не обещает.
