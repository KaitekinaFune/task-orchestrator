# Taskroom / Task Orchestrator

Локальный дашборд для задач AI-агентов: поручить работу в репозитории, наблюдать за этапами и продолжить разговор. Рабочее название интерфейса — Taskroom; первый milestone находится в разработке.

Идея: создать задачу в локальном веб-интерфейсе, поручить её Claude Code или Codex, наблюдать за ходом работы или подключиться через терминал, затем получить независимое ревью выбранным агентом и краткий отчёт. Код, состояние, рабочие директории и логи остаются локально; сами агенты могут обращаться к своим внешним API.

## Состояние

Доступны подключение Git-репозитория, сохраняемые задачи, профили Claude, запуск в текущем checkout и настроенные проверки с живым выводом, остановкой и историей результатов. Доступны исполнитель Codex и независимое ревью Codex. Терминал и worktree ещё не реализованы. Реальный минимальный запуск по подписке и следующий за ним прогон проверок проверены на Windows; обращения через DeepSeek пока не проверены; LiteLLM проверен запуском команды в режиме `auto`. Подробности — в [проверке среды](docs/ENVIRONMENT.md).

Кнопка «Показать Git-состояние» читает текущую ветку, HEAD и список staged, unstaged и untracked файлов. Поддерживаются новый репозиторий без коммитов, detached HEAD и переименования. Эта кнопка содержимое файлов не сохраняет; копии создаются только при запуске агента (см. «Снимки и diff»). Создание worktree ещё не реализовано.

## Запуск задачи

При создании выберите процесс отдельно от профиля Claude:

- **Один агент** — исходный выбор для новых задач. Только исполнитель, без автоматических проверок оркестратора и независимого ревью; подходит для небольшой локальной правки. Пропущенные по выбору этапы отмечены «не запрошены», а не «успешны».
- **Агент + выбранные проверки** — тот же исполнитель и отмеченные команды проекта. Можно оставить только компиляцию, не запуская остальные проверки. Нужна хотя бы одна доступная проверка. Независимое ревью не запускается.

Режим виден в задаче, предпросмотре и истории попытки. Старые задачи без режима продолжают использовать все проверки проекта; они не переводятся в быстрый режим автоматически. Режим «Агент + проверки + ревью» запускает отдельного Codex после исполнителя и выбранных проверок. Проверки можно не выбирать; это не считается успешной проверкой. Автоматические исправления включаются отдельно; см. раздел ниже. Выбор процесса не меняет защиту CLI, проверку Git-состояния и права на commit/push/merge. Исправлять код текущей MR-ветки можно как обычную локальную задачу; интеграция с MR и публикация изменений пока не реализованы.

На главном экране выберите проект, напишите задачу и нажмите «Продолжить». Откроется страница задачи, и агент запустится сразу, если в checkout нет незакоммиченных изменений. Если они есть, сначала будет показан экран запуска со списком изменений и кнопкой «Запустить Claude» или «Запустить Codex»; он действует пять минут. Файл, сохранённый после показа экрана, не мешает запуску и просто войдёт в исходное состояние, а смена ветки или HEAD требует новой подготовки. При продолжении разговора подтверждение спрашивается, только если файлы изменились после прошлого ответа. Подключая репозиторий, вы подтверждаете, что доверяете ему. Git submodules полностью игнорируются: они не блокируют запуск и не влияют на актуальность результатов, а приложение их не инициализирует и не обновляет. Списки Git читаются потоком без лимита общего вывода 4 МБ; файлы хешируются группами до 16 одновременно. Чтение не атомарно и не защищает от внешних редакторов: не меняйте файлы во время подготовки и выполнения. Игнорируемые Git файлы не входят в сравнение. На крупном Unity-репозитории подготовка может занимать десятки секунд.

Одновременно допускается одна попытка на весь экземпляр сервера. Claude запускается напрямую, без shell и пользовательских PowerShell-функций, с `--print --output-format stream-json --verbose --permission-mode <режим> --permission-prompts none`. Для подписки и LiteLLM режим — `auto`: обычные действия, включая правку файлов, команды и сетевые запросы, CLI разрешает сам с помощью своего классификатора. Для DeepSeek — `acceptEdits`: файлы правятся, но команды, требующие подтверждения, отклоняются. Bypass не используется. Отклонённые действия показываются в задаче со статусом «требуется решение» вместе с точным правилом, а «Разрешить и продолжить» запускает новый ход той же сессии с этим правилом. Так не разрешить правки файлов и команды со скрытыми секретами, в несколько строк или с `$`, скобками и обратными кавычками: CLI не примет для них точное правило. CLI может отказать и при выданном правиле из-за проверки путей записи; тогда выполните действие вручную. Запускайте только доверенные репозитории: CLI может загрузить настройки, hooks и MCP из проекта и окружения пользователя. Аргументы сверены с установленным Claude Code 2.1.317 и [официальной документацией](https://code.claude.com/docs/en/headless).

События и текстовые сообщения Claude обновляются опросом API каждые 750 мс; это вывод процесса, не интерактивный терминал. Журнал и события сохраняются в том же `state.json` с интервалом до 500 мс и при завершении. Ответ агента и диагностика CLI (stderr) показываются отдельно; каждый журнал ограничен 256 Ки символов (сохраняются начало и конец, пропуск середины отмечен), события — первыми 200 с явной отметкой об ограничении. Финальное поле `result`, повторяющее последнее сообщение `assistant`, не печатается второй раз; отличающийся финальный текст сохраняется. Известные значения ключей и токенов из окружения скрываются в обоих журналах; это не гарантирует удаления произвольных секретов из ответов модели. Старые сохранённые журналы не переписываются: в них предупреждения и дублирование могут сохраниться.

Код 0 и корректный финальный результат означают завершение процесса, но не выполнение задачи: агент мог вернуть вопрос или частичный ответ. Интерфейс явно показывает, что результат задачи не подтверждён. Автоматического распознавания вопросов нет. Если CLI вернул ID сессии, после завершения доступна форма «Продолжить разговор»: сообщение запускает новый ход в той же сессии: Claude `--resume` или Codex `exec resume`. Подтверждение спрашивается, только если файлы изменились после прошлого ответа. Сессия сохраняется и после ошибки или остановки хода, поэтому разговор можно продолжить; продолжение после принудительной остановки на реальном CLI пока не проверено, и если оно не удастся, ход завершится ошибкой. Во время работы форма недоступна; разрешение на отклонённое действие выдаётся следующим ходом. После завершения CLI этап чтения Git-состояния может занимать десятки секунд; это не продолжение работы агента. Затем в режиме с проверками запускаются только подтверждённые выбранные команды. В быстром режиме проверки и ревью — «не запрошены»; у старых задач без конфигурации проверок — «не настроены». Даже успешные проверки не подтверждают все критерии задачи автоматически. Вывод не используется как команды.

«Остановить» завершает дерево процессов через Windows `taskkill /T /F`; автоматический лимит — 30 минут. Завершение процесса и состояние файлов сохраняются раздельно. Ошибка сохранения останавливает агента и блокирует новые попытки до перезапуска. После аварийного завершения сервера незавершённая попытка становится прерванной: перед новым запуском необходимо вручную проверить остановку старых процессов и подтвердить это в интерфейсе. Автоматического восстановления сессии нет.

До и после запуска сохраняются SHA-256 идентификатор состояния и снимок файлов. Сравнение не охватывает игнорируемые файлы. Результаты проверок относятся только к совпавшему состоянию учтённых файлов на момент последнего сравнения.

## Снимки и diff

В каждом ходе задачи есть раздел «Изменения файлов за этот ход»: разница между снимками до запуска и после завершения исполнителя, с автоматическими исправлениями этого хода. Показываются статус файла, число строк и текст изменений. Если checkout был грязным, отдельно доступны «Незакоммиченные изменения до запуска»: разница между HEAD и исходным снимком. Они не входят в diff хода, но правку агента поверх той же строки или файла diff хода покажет только как разницу двух снимков. Правки, сделанные вне агента во время запуска, отделить нельзя, и они попадут в diff; внешнее редактирование нельзя исключить и при чистом checkout. Если агент изменил HEAD, приложение об этом предупредит, и в diff войдёт закоммиченное содержимое.

Снимок — Git-дерево, собранное временным индексом с копией неигнорируемых изменённых и untracked файлов. Индекс и `.git/objects` репозитория не меняются, хотя настроенные фильтры, например Git LFS, работают как при обычном `git status`. Копии лежат в `.data/app/snapshots/<id задачи>` и могут содержать всё, что Git не игнорирует, включая незакоммиченные файлы с секретами. Автоматически они удаляются только вместе с задачей или проектом; файлы защищены не больше, чем `state.json`. Восстановления файлов из снимка нет.

Diff остаётся прежним после последующих правок: он показывает снимки, а не текущие файлы. Вместо него показывается причина, если снимок создать не удалось (например, изменённые файлы занимают больше 512 МиБ), попытка создана до появления снимков или нужные объекты удалены из Git после переписывания истории и очистки. Ошибка снимка не останавливает агента. Текст изменений ограничен 4 МиБ на diff, список файлов при этом полный. Игнорируемые файлы и submodules не входят. Внешние diff-драйверы и textconv при просмотре отключены. Снимок снимается сразу после сравнения файлов, но не атомарно с ним. Ревьюер пока не получает этот diff и оценивает весь checkout.

## Дашборд и пресеты

- **Обзор** — постановка задачи, фильтры-счётчики по статусу и поиск. Название и отдельные критерии необязательны; задание хранится полностью. От 1360 px форма новой задачи закреплена в правой колонке, у́же она сворачивается в строку над списком и раскрывается при вводе. Задачи показываются списком или доской по статусам; от 1600 px по умолчанию выбрана доска. Выбор вида и темы (тёмная по умолчанию, светлая или как в системе) запоминается в браузере.
- **Проекты** — подключение локального репозитория, настройка проверок и раздел «Процессы в этом проекте»: процесс по умолчанию и то, какие проверки запускает каждый процесс. Пока выбор не сделан, запускаются все проверки проекта, включая добавленные позже. Процесс, которому нужны проверки, не создаст задачу в проекте без них.
- **Процессы** — создать или изменить именованный пресет, общий для всех проектов: исполнитель Claude/Codex, профиль и модель, этапы, инструкции и параметры независимого ревьюера. При необходимости — свой граф шагов (см. ниже). Созданные задачи сохраняют свою копию настроек и списка проверок.

Если в состоянии есть пресеты старого формата, привязанные к проектам, сервер перенесёт их при запуске и сохранит прежний файл как `.data/app/state.before-global-presets.json`. Полностью совпадающие пресеты объединяются, а прежний выбор проверок остаётся в каждом проекте. Откатиться на старую версию приложения с новым `state.json` нельзя: для этого нужна эта копия.
- **Подключения** — параметры подписки, LiteLLM и DeepSeek.

Задачи, процессы и проекты удаляются кнопкой «Удалить»: первое нажатие только просит подтвердить, отмены нет. Задача удаляется вместе со своей историей и снимками, проект — вместе со всеми своими задачами, но не с процессами. Удаление процесса сбрасывает его как процесс по умолчанию во всех проектах. Файлы репозитория не затрагиваются. Задача с идущим запуском не удаляется. Созданные задачи сохраняют свою копию настроек удалённого процесса.

В странице задачи видны исполнитель, порядок этапов, последний этап, события, ответы и результаты проверок. После завершения можно продолжить сохранённую сессию либо начать заново. Доступен независимый ревьюер; агент, профиль, модель и инструкции настраиваются отдельно от исполнителя. Продолжение Claude по подписке и Codex проверено реальными smoke-сценариями; LiteLLM и DeepSeek не проверены.

## Codex и ревью

В «Процессах» выберите исполнителя, профиль и при необходимости модель. Для Codex используется стандартная авторизация установленного CLI; «Подключения → Проверить вход Codex» проверяет её статус, а не доступ к конкретной модели.

Для независимого ревью выберите этапы «Исполнитель → проверки → ревью», затем агента, профиль и модель ревьюера: подойдёт любой агент, включая Claude через LiteLLM или DeepSeek. Ревьюер получает отдельную сессию и инструкции. Исполнитель Codex работает с `workspace-write`, ревьюер Codex — с `read-only`, ревьюер Claude — в режиме `plan` без инструментов правки; дополнительные права не выдаются. Приложение не отключает ограничения CLI.

При автоматических исправлениях можно выбрать, кто исправляет: исполнитель в своей сессии (по умолчанию) или другой агент в новой сессии. Ручное продолжение разговора всегда идёт в сессию исполнителя.

`bun run smoke:claude-review` — явная проверка ревьюера Claude на реальной модели: структурированный отчёт и запрет записи во временном репозитории. Требует авторизации Claude и расходует лимит модели.

В задаче появляются итог ревью, оценка каждого заявленного критерия, замечания с файлами/строками, ограничения и актуальность. Ревью охватывает весь текущий checkout, включая ранее существовавшие изменения. Его результат не означает принятия задачи. Повреждённое или противоречивое заключение — ошибка; unknown остаётся неподтверждённым. Актуальность сверяется автоматически при открытии задачи. Повторные проверки после ревью делают старое заключение устаревшим.

«Передать замечания исполнителю» подготавливает новый ход в его исходной сессии. Отчёт передаётся в контекст автоматически; подтверждение нужно, только если файлы изменились после прошлого ответа. Для автоматического продолжения заранее включите его в настройках процесса с ревью. Если ревью не удалось, сообщение можно отправить обычной формой продолжения.

`bun run smoke:codex` — отдельная явная проверка с настоящими моделями: исправление функции сложения во временном репозитории, настроенный тест, независимое ревью, продолжение сессии и обнаружение устаревшего результата. Требует авторизации Codex и расходует лимит модели. Заключение ревьюера может быть неполным или содержать замечания — smoke проверяет корректный протокол и состояние, а не принудительное одобрение.

## Команды проверок

В списке проектов раскройте «Настроить команды проверок» и сохраните JSON-массив. Команды запускаются в корне выбранного проекта с правами текущего пользователя. Например, для этого репозитория:

```json
[
  {
    "id": "tests",
    "name": "Тесты",
    "executable": "bun",
    "args": ["run", "test"],
    "timeoutSeconds": 600
  }
]
```

Для своего проекта укажите его реальную команду, доступную в PATH процесса сервера, либо полный путь к executable. Поддерживается до 12 проверок, таймаут каждой — 1–3600 секунд. `[]` означает отсутствие проверок. Не помещайте секреты в название, executable или args: эти параметры сохраняются в истории. Каждая команда и директория показываются перед подтверждением. Изменения настроек во время работы применяются к следующим запускам; текущая попытка использует подтверждённые определения.

Shell автоматически не запускается: `executable` и каждый элемент `args` передаются напрямую. `.bat`/`.cmd` нельзя указывать как executable. Для них или PowerShell-скриптов явно настройте `powershell.exe` с `-NoProfile -NonInteractive` и аргументами скрипта. При запуске внешней программы через PowerShell завершайте обёртку `exit $LASTEXITCODE`, чтобы её код выхода не потерялся. Сохранённые API-ключи Claude из Windows Credential Manager в окружение проверок не передаются; окружение сервера очищается от известных переменных профилей Claude. Произвольные настройки окружения команды в интерфейсе пока не реализованы.

В режиме с проверками после успешного Claude выбранные команды выполняются по очереди в порядке настроек проекта. Ненулевой код сохраняется как ошибка, следующие независимые проверки продолжаются; ошибка запуска не получает вымышленного exit code. Отмена или таймаут останавливают текущий процесс и не запускают оставшиеся команды. Каждая проверка хранит точное определение, время, реальный код выхода/сигнал, объединённый stdout/stderr до 256 Ки символов (начало и конец, середина пропускается) и привязку к отпечатку результата Claude. Если определение снимка невозможно, результат — «непроверены». Файлы сравниваются один раз в конце прогона, а в режиме с ревью — в конце ревью: при изменении результаты — «устарели», при этом все выбранные команды уже выполнены. Игнорируемые Git файлы не учитываются; команды, создающие такие артефакты, не меняют отпечаток. Если выбранный профиль удалён, запуск блокируется с понятной причиной, а не продолжается без проверки.

У последней завершённой попытки можно нажать «Подготовить проверки», чтобы выполнить команды без повторного обращения к Claude. Для режима с выбранными проверками повторяются только выбранные профили; для быстрого режима это отдельный подтверждаемый запуск команд проекта. Требуется совпадение текущих файлов с результатом этой попытки; состав команд снова показывается и подтверждается. История предыдущих прогонов сохраняется. При открытии задачи и при возвращении на страницу, не чаще раза в 30 секунд, результаты последней попытки сравниваются с текущими файлами без учёта submodules: изменение отмечается как устаревание, ошибка чтения — как непроверенное состояние. Постоянного наблюдения за файлами нет; рядом с результатом показано время последнего сравнения. Успех команды относится к этому моменту, а не к любым последующим изменениям.

## Запуск и проверка

Нужны Node.js 22 или новее, Git и Bun. Сервер работает на Node.js. happy-dom используется только для DOM-тестов; зависимости устанавливаются через Bun. В PowerShell из директории проекта:

```powershell
bun install
bun run start
bun run test
```

Дополнительно `bun run smoke:claude` выполняет реальное обращение к модели через профиль подписки: создаёт отдельный временный репозиторий, поручает прочитать тестовый файл, проверяет ответ и неизменность файлов, запускает настроенную проверку с кодом 0, продолжает точную сессию и проверяет воспоминание предыдущего ответа без повторного чтения файла, повторяет проверку без Claude с ожидаемым кодом 7, затем меняет тестовый файл и проверяет устаревание результатов. После этого удаляется только временный каталог. Требует рабочей авторизации Claude и может расходовать лимит подписки. Обычный `bun run test` использует тестовые дочерние процессы и не вызывает модели. Bun lockfile сохранён в `bun.lock`. Тесты интерфейса проверяют формы, маршруты и продолжение разговора в DOM; это не заменяет визуальную проверку в браузере.

Откройте адрес, выведенный сервером (по умолчанию `http://127.0.0.1:3000`). Сервер работает только пока запущен процесс. Данные находятся в `.data/app/state.json`; резервное копирование, удаление истории и защита файла средствами Windows пока не реализованы. Не запускайте несколько экземпляров с одной директорией данных. Значения `PORT` и `TASK_ORCHESTRATOR_DATA` при необходимости задаются переменными окружения.

## Профили Claude

Для LiteLLM один раз заполните URL и имена моделей в разделе «Корпоративный LiteLLM» и отдельно сохраните API-ключ. Параметры записываются в локальный файл состояния, ключ — в Windows Credential Manager текущего пользователя под именем `TaskOrchestrator/LiteLLM`. Пустое поле ключа не меняет сохранённый ключ; отдельное сохранение заменяет его. Поля модели и URL не предназначены для секретов. При необходимости ключ можно удалить через диспетчер учётных данных Windows.

Для личного DeepSeek используйте отдельный раздел: кнопка шаблона подставляет несекретные параметры из функции `claude-ds`, после чего их нужно сохранить и отдельно ввести ключ. Он хранится под именем `TaskOrchestrator/DeepSeek`, независимо от ключа LiteLLM. Проверка показывает наличие необходимых настроек и ключа, но не обращается к модели. DeepSeek — отдельный профиль Claude, не подключение самостоятельного CLI DeepSeek.

Дополнительно доступны пары имён переменных окружения и шаблон, составленный по PowerShell-профилю. Имена без источника только очищаются. Значения источников наследуются при запуске сервера; сохранённые параметры LiteLLM и ключ имеют приоритет. Укажите полный список переменных, которые следует удалять из окружения подписки. Сервер не вызывает пользовательские функции PowerShell.

Кнопка подписки запрашивает статус авторизации у установленного Claude CLI в подготовленном окружении; сам этот ответ не подтверждает вызов модели. Кнопка LiteLLM проверяет только наличие настроек и ключа, не доступность сервиса и не действительность ключа. При запуске задачи выбранный профиль формирует отдельное окружение, а сохранённый ключ читается из Windows Credential Manager. Реальный вызов DeepSeek пока не проверен. Процессы текущего пользователя могут иметь доступ к его учётным данным согласно настройкам Windows.

## Автоматические исправления

В процессе «С независимым ревью» можно выбрать до трёх исправлений после первого прохода, общий лимит 5–120 минут и причины продолжения: ошибки проверок, замечания ревью или обе. По умолчанию выбран ручной режим. Лимиты показываются до подтверждения запуска и сохраняются в задаче; редактирование пресета влияет только на новые задачи.

Каждое исправление продолжает сессию исполнителя или выбранного агента исправлений, повторяет выбранные проверки и независимое ревью. На странице задачи видны номер прохода, срок, причина остановки, предыдущие ответы и отчёты. Неполное ревью, неопределённые критерии, недостоверные проверки, повторение проблем, отсутствие прогресса или изменение файлов/конфигурации между проходами останавливают автоматическое продолжение для решения человеком. Успешное ревью означает готовность к рассмотрению, а не принятие результата.

«Не продолжать автоматически» позволяет завершить текущий проход и запрещает новые исправления. «Остановить» прерывает текущий процесс. После перезапуска сервера цикл сам не возобновляется. Автоматизация проверена тестовыми дочерними процессами и DOM-тестами; полный автоматический цикл с реальными моделями пока не проверен.

## Граф шагов (необязательно)

Для обычной задачи ничего настраивать не нужно: она начинается как «Один агент». Граф нужен, когда над задачей работает несколько ролей. В «Процессы» → «Этапы» выберите «Свой граф шагов», начните с шаблона и настройте шаги. Задача использует граф, только если выбрать такой процесс. Над шагами показана схема маршрута: пунктир обозначает переход при проблемах, клик по шагу открывает его настройки. На странице задачи та же схема показывает, где процесс сейчас и чем закончился каждый шаг; клик открывает результат шага. Менять связи на самой схеме нельзя, они задаются в форме шага.

Типы шагов: исполнитель, другой пишущий агент, роль только на чтение с ответом текстом, ревью из 1–4 ролей (работают одновременно), проверки проекта и подтверждение человека. Роль ревью либо блокирует результат от выбранной важности, либо совещательная: её мнение показывается пользователю, но не влияет на готовность и не передаётся пишущим агентам.

Для каждого шага задаётся следующий шаг, а для ревью, проверок и подтверждения ещё и шаг на случай проблем. Без него решение остаётся за вами. Следующий шаг определяют коды выхода и заключения, а не текст агента. Процесс останавливается для решения человека при неполном заключении, повторении тех же проблем, отсутствии изменений после исправления, правке файлов между шагами, исчерпании повторов или общего времени.

Пока шаг ждёт подтверждения, ничего не запущено и файлы можно менять; ожидание переживает перезапуск сервера. Кнопки «Не продолжать автоматически» и «Остановить» работают как в обычном процессе, у каждого пишущего шага виден свой diff. Продолжение разговора идёт в сессию исполнителя и начинается с его шага. Записывает всегда один агент за раз; права CLI граф не расширяет.

Граф проверен тестовыми процессами, DOM-тестами и просмотром интерфейса в браузере. С реальными Claude и Codex он пока не запускался.
